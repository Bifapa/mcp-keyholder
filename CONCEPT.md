# MCP Keyholder — концепция

Локальный менеджер секретов для AI-агентов. Хранит ключи зашифрованными, выдаёт их агентам по MCP только в рамках разрешений, которые подтвердил человек, и записывает каждое обращение в журнал. Работает на Windows и macOS.

Дизайн-макеты (светлая и тёмная темы): https://claude.ai/artifact/HNQY7AmiFoMZ76c4h81su4

---

## 1. Зачем

Сейчас ключи лежат в папке `KEYS` в `.txt`. Любой агент, любой скрипт и любая программа, запущенная под пользователем, может их прочитать. Никто не знает, кто и когда их брал. Важные ключи (GitHub, DNS, подпись релизов) защищены так же, как неважные.

**Цели**

1. Ключи хранятся только в зашифрованном виде.
2. Агент получает ключ только через KeyHolder, и только тот, который входит в одобренное разрешение.
3. Важные ключи требуют подтверждения, которое агент не может выполнить сам (код с телефона, позже — Touch ID / Windows Hello).
4. Для важных ключей есть режимы, в которых значение вообще не попадает к агенту (заглушка + прокси, подпись).
5. Каждое обращение, отказ и подтверждение записываются в журнал, который нельзя незаметно подправить.
6. Если ключ всё-таки утёк, это видно сразу: агент может сам сообщить, KeyHolder может найти значение в тексте.

**Не цели**

- Синхронизация между устройствами, общий доступ для команды — не в первой версии.
- Защита от злоумышленника с правами администратора/root на этой машине. Это невозможно для любого локального приложения (подробности в §11.18).

## 2. Как это выглядит

**Добавить ключ.** Окно «Новый ключ»: имя (`github/pipod-updates`), значение, описание (его увидит агент), группа, уровень подтверждения, режим выдачи. Импорт из `.txt` — дополнительная функция: KeyHolder находит в файле похожие на ключи фрагменты, остальное вырезается, черновики правятся пачкой.

**Агент работает.**
1. Агент вызывает `list_secrets` — видит имена и описания, без значений.
2. Агент вызывает `request_grant` со списком ключей, режимами и причиной.
3. На экране появляется окно подтверждения. Для обычных ключей — кнопка «Разрешить», для важных — поле для кода из приложения-аутентификатора.
4. Агент получает разрешение на N минут и работает только с этими ключами. Любой другой ключ — отказ.

**Если ключ засветился.** Агент вызывает `report_leak` с комментарием — в таблице у ключа появляется красный «!», в трее уведомление. Или агент передаёт подозрительный текст в `check_leak` — KeyHolder сам находит в нём свои значения и помечает ключи.

## 3. Архитектура

```
 Агенты (Claude Code, Cursor, …)                 Пользователь
   │ MCP stdio                                       │
   ▼                                                 ▼
 kh mcp (шим, по процессу на агента)          KeyHolder.app (Tauri, трей)
   │ named pipe / unix socket                        │ in-process команды
   ▼                                                 ▼
 ┌─────────────────────────── ядро KeyHolder ───────────────────────────┐
 │ хранилище · политика · разрешения · OTP · журнал · поиск утечек ·     │
 │ прокси подстановки (127.0.0.1) · подпись · ssh-agent                  │
 └──────────────────────────────────────────────────────────────────────┘
   ▲
   │ kh run --ticket … -- git push      (дочерний процесс видит только заглушки)
```

**Компоненты**

| Компонент | Что делает | Где работает |
|---|---|---|
| Ядро | Хранилище, политика, разрешения, журнал, прокси | Внутри приложения (портативный режим) или отдельной службой (защищённый режим, §11.4) |
| KeyHolder.app | Трей, главное окно, окна подтверждения | Сессия пользователя |
| `kh mcp` | MCP-сервер по stdio для агента; пересылает вызовы ядру по локальному каналу | Запускается агентом |
| `kh run` | Запускает команду с заглушками и прокси (или с переменными окружения) | Запускается агентом |
| `kh scan` | Ищет значения ключей в файлах (например, в истории агентов) | Запускает пользователь |

**Почему ядро — отдельный слой, а не «MCP-сервер с базой».** Одно открытое хранилище на машину; разрешения и аренды общие; MCP-шим не имеет доступа к базе и ключам, он только передаёт запросы.

**Почему MCP только через stdio.** HTTP-MCP на `localhost` открывает целый класс атак (DNS rebinding, CSRF из браузера). Шим по stdio + named pipe / unix socket этого класса не имеет.

## 4. Модель данных

```
secrets   id, name, description, group, tags, tier, allowed_modes, status,
          proxy_hosts, proxy_header, path_rules, partition,
          ciphertext, nonce, policy_mac, version, created_at, updated_at, last_used_at
groups    id, name, description, default_tier, default_ttl, max_ttl
clients   id, name, token_hash, visible_groups, created_at, revoked_at
presets   id, name, reason, keys[{name, mode}], ttl
grants    (в памяти) id, client_id, session_id, keys[{name, mode}], expires_at, uses
leaks     id, secret_id, kind (reported|found|exposed), client, session, comment, at, resolved_at
audit     seq, ts, client, session, action, target, outcome, detail, prev_hash, hash, mac
settings  kdf_params, wrapped_keys, totp_seed_enc, totp_last_step, recovery_hashes,
          antiphish_word_enc, autolock_min, counters …
```

Имя ключа — только `[a-z0-9._/-]`, до 64 символов (без «похожих» Unicode-символов и управляющих последовательностей).

## 5. Уровни подтверждения и режимы выдачи

**Уровень** — что нужно, чтобы ключ попал в разрешение.

| Уровень | Окно | Кто может подтвердить |
|---|---|---|
| `auto` (Без окна) | нет, только журнал | — |
| `soft` (Мягкое) | кнопка «Разрешить» | человек, но и агент через UI-автоматизацию (это защита от случайностей, не от агента) |
| `otp` (OTP) | поле для кода | только тот, у кого телефон с аутентификатором |
| `sealed` (Запечатан) | — | агенту никогда; человеку — в главном окне после повышения прав |

**Режим выдачи** — в каком виде агент получает ключ.

| Режим | Что видит агент | Значение покидает ядро? |
|---|---|---|
| `reveal` | значение в ответе MCP (и в истории чата) | да |
| `env` | значение в окружении процесса `kh run` | да (считается раскрытием) |
| `proxy` | заглушку; настоящее значение подставляет прокси по пути к разрешённому хосту | нет |
| `sign` | только подписи | нет |
| `recipe` | только результат заранее заданной команды (команда получает заглушки + прокси) | нет |

Правила по умолчанию: ключам уровня `otp` разрешены только `proxy`/`sign`/`recipe`. Включить `reveal`/`env` для `otp`-ключа можно, но только с повышением прав (§11.9) и с предупреждением. Если в одном запросе ключи разных уровней — показывается окно самого строгого.

## 6. Разрешения (grants)

- Агент подаёт запрос: причина, список `{ключ, режим}`, срок. Или ссылка на пресет.
- Человек в окне может снять галочки с части ключей и сократить срок. Добавить ключи или удлинить срок из окна нельзя — только новым запросом.
- Разрешение привязано к одной MCP-сессии (одному процессу `kh mcp`) и токену клиента. Закрыл агент сессию — разрешение умерло.
- Режим в разрешении не может быть мягче, чем разрешено ключу; агент не может «повысить» `proxy` до `reveal`.
- Всё, чего нет в разрешении, — отказ `not_in_grant` с записью в журнал.
- Пресет только заполняет список; подтверждение всё равно нужно каждый раз.
- Разрешение заканчивается по сроку, по закрытию сессии, по отзыву из интерфейса и при блокировке хранилища.

Защита от спама: одно окно на экране, остальные в очереди; одинаковые запросы склеиваются; не больше 5 запросов в минуту на клиента; кнопка «Отклонить и заблокировать сессию на 10 мин».

## 7. MCP-инструменты

| Инструмент | Что делает |
|---|---|
| `list_secrets(group?, query?)` | Имена, описания, группа, уровень, допустимые режимы, статус (`ok` / `exposed` / `leaked` / `disabled`), входит ли в текущее разрешение. `sealed` не показываются. |
| `request_grant(reason, keys[{name, mode}], ttl_minutes?)` или `request_grant(reason, preset)` | Ждёт решения человека до 3 минут. Ответ: `granted` (итоговый список, срок, что убрано и почему) / `denied` / `timeout` / `rate_limited` / `locked`. |
| `my_grants()` | Активные разрешения этой сессии. |
| `get_secret(name)` | Значение — только для ключа в режиме `reveal` внутри активного разрешения. Ключи `auto` получают разрешение автоматически. |
| `prepare_run(keys[], command?)` | Одноразовый билет для `kh run` (режимы `env`/`proxy`/`recipe`). Срок жизни билета — 60 секунд, он привязан к разрешению. |
| `report_leak(name, comment)` | Агент сообщает, что ключ оказался у него на виду. |
| `check_leak(text)` | Ищет в тексте значения ключей хранилища; найденные ключи помечаются слитыми. Возвращает только имена. |

Инструмента «ввести OTP» **нет** намеренно (почему — §11.7).

## 8. CLI

```
kh mcp                         MCP-сервер для агента (токен клиента — в переменной KH_TOKEN)
kh run --ticket T -- <команда>  запустить команду с заглушками/прокси или env
kh scan <путь>…                найти значения ключей в файлах
kh status                      состояние ядра
```

Все действия управления (добавить, изменить, удалить, посмотреть значение) — только в главном окне. У CLI нет пути к значению, который обходил бы разрешения.

## 9. Утечки

У ключа три статуса, связанных с утечкой:

| Статус | Когда ставится | Цвет |
|---|---|---|
| `exposed` (раскрыт агенту) | автоматически при выдаче в режиме `reveal` или `env` — значение покинуло ядро | жёлтый |
| `leaked` (слит) | агент вызвал `report_leak` или `check_leak` / `kh scan` нашёл значение | красный «!» |
| сброшен | пользователь заменил значение (ротация) или снял отметку с повышением прав | — |

**`report_leak(name, comment)`** — агенту выгоднее сообщить, чем промолчать: в инструкции инструмента прямо сказано, что это правильное поведение. Комментарий показывается с пометкой «со слов агента». Ограничение — 10 сообщений в час на сессию. Автоматически ключ **не отключается** (иначе агент мог бы так «выключать» ключи); есть настройка «отключать при сообщении об утечке», по умолчанию выключена.

**`check_leak(text)`** вместо инструментов «посчитать хэш» и «сравнить хэш»:
- «Хэш строки» агенту не нужен: строка у него и так есть.
- Сравнение по хэшу требует хранить или отдавать хэши значений. Хэш слабого значения (пароля) перебирается офлайн, а API «совпадает ли хэш» — это тихий оракул.
- `check_leak` получает весь текст, ищет полные значения (и их base64, base64url, hex, URL-кодированные формы) и возвращает только имена. Любое совпадение сразу поднимает тревогу у человека, поэтому пользоваться им как оракулом незаметно нельзя.
- Значения короче 16 символов и низкой энтропии (пароли, PIN) в поиске не участвуют — для них оракул опасен.
- Лимиты: 1 МБ текста за вызов, 20 вызовов в час на сессию.

**Слепые зоны поиска** (их нужно понимать): значения короче 16 символов и низкой энтропии не ищутся никогда; ищутся только перечисленные кодировки. Агент, который уже держит значение, может его «упаковать» (gzip, разбить, перевернуть) — такой текст поиск не найдёт. `check_leak` — помощник для честного агента и для человека, а не детектор против злонамеренного.

**`kh scan`** — тот же поиск для пользователя. Например, `kh scan ~/.claude/projects` покажет, какие ключи когда-либо попадали в историю агентов.

## 10. Интерфейс

Экраны: трей, ключи (таблица, фильтры, массовое редактирование), новый ключ, разрешения (очередь, активные, пресеты, блокировки), клиенты, журнал, импорт, настройки. Окна подтверждения двух типов: мягкое и с OTP. Светлая и тёмная темы, акцент — фиолетовый. Макеты — по ссылке в начале документа.

## 11. Безопасность

### 11.1 Что гарантируем

1. Значение ключа не лежит на диске в открытом виде — нигде, никогда.
2. Агент не может получить ключ уровня `otp` без кода, который физически есть только на телефоне человека.
3. Ключ в режиме `proxy`/`sign`/`recipe` не покидает ядро: ни через MCP, ни через CLI, ни через окружение процессов.
4. Ключ `sealed` не выдаётся агентам ни в каком виде.
5. Любое изменение, ослабляющее защиту (понизить уровень, сменить режим на `reveal`, добавить хост в прокси…), требует повышения прав: мастер-пароль + OTP.
6. Каждое обращение, отказ и подтверждение попадают в журнал; удаление или правка записей обнаруживается.
7. Нет ни одного пути к значению, который обходит окно подтверждения.

Гарантии 2–6 в полном объёме действуют только в **защищённом режиме установки** (§11.4).

**Честно про портативный режим (v0.1).** Он защищает от агента, который пользуется MCP, файлами, командами и окнами: такой агент не получит `otp`-ключ без кода, не ослабит политику правкой базы, не подделает журнал правкой базы. Но на Windows любой процесс того же пользователя может **прочитать память KeyHolder.app**. Противник, который сознательно это делает, получает всё: расшифрованные ключи, секрет TOTP (и может сам генерировать коды), `K_policy` (подпишет ослабленную политику) и `K_log` (подделает журнал). Ещё он может подменить сам `KeyHolder.exe`, потому что тот лежит в каталоге пользователя. От такого противника защищает только защищённый режим.

### 11.2 Модель угроз

**Что защищаем:** значения ключей; мастер-пароль и ключи шифрования; секрет TOTP; закрытый ключ локального УЦ прокси; целостность политики и журнала.

**От кого:**

| # | Противник | Что умеет | Насколько опасен |
|---|---|---|---|
| A1 | Агент, сбитый prompt injection (из README, issue, веб-страницы) или просто ошибающийся | Вызывать MCP, запускать команды в shell, читать файлы пользователя, управлять окнами (computer use), делать скриншоты | Главная угроза |
| A2 | Вредоносная программа под тем же пользователем | Всё, что A1, плюс читать память процессов пользователя (Windows), ставить клавиатурные хуки, подменять файлы в каталогах пользователя | Высокая |
| A3 | Доступ к диску: украденный ноутбук, бэкап, синхронизация папок | Читать и копировать файлы офлайн | Средняя |
| A4 | Веб-страница в браузере | Стучаться на `127.0.0.1`, DNS rebinding | Средняя |
| A5 | Атакующий в сети | Подменять DNS, перехватывать трафик | Средняя |
| A6 | Цепочка поставок | Вредоносная зависимость, подмена обновления | Средняя |
| A7 | Администратор / root на машине | Всё | Вне модели (§11.18) |

**Допущения:** ОС не скомпрометирована на уровне ядра; агент не запущен с правами администратора/root; UAC не выключен; у пользователя нет `sudo` без пароля; телефон с аутентификатором не скомпрометирован.

### 11.3 Главный принцип

Агент работает от имени пользователя и может всё, что может пользователь в своей сессии. Поэтому защита держится только на том, **чего у агента нет**:

- кода с телефона (OTP);
- пальца или лица (Touch ID / Windows Hello, позже);
- границы между учётными записями ОС (ядро под отдельной системной учёткой);
- мастер-пароля, который вводится редко.

Всё, что может сделать «нажатие кнопки» или «прочитать файл пользователя», агент тоже может сделать. Поэтому мягкое подтверждение — не защита от агента, а файлы и память процессов пользователя не считаются надёжным местом для секретов.

### 11.4 Границы доверия и режимы установки

```
┌──────────── учётка KeyHolder (служба) ────────────┐   ┌──── пользователь ────────────────────┐
│ ядро: база, ключи в памяти, TOTP, журнал, прокси  │◄──┤ KeyHolder.app (UI), kh mcp, kh run,  │
│ база: %ProgramData%\KeyHolder (ACL: только служба)│   │ агенты, браузер, всё остальное        │
└───────────────────────────────────────────────────┘   └──────────────────────────────────────┘
```

| | Защищённый режим | Портативный режим |
|---|---|---|
| Где работает ядро | Служба Windows под виртуальной учёткой `NT SERVICE\KeyHolder`; на macOS — LaunchDaemon под пользователем `_keyholder` | Внутри KeyHolder.app под пользователем |
| Где лежит база | `%ProgramData%\KeyHolder` / `/Library/Application Support/KeyHolder`, доступ только у службы | `%APPDATA%\KeyHolder` / `~/Library/Application Support/KeyHolder` |
| Нужны права администратора | Один раз при установке | Нет |
| Может ли процесс пользователя прочитать память ядра | Нет (граница учётных записей) | Windows: да, тот же пользователь может читать память процесса. macOS: нет, если приложение подписано с hardened runtime (без `get-task-allow`) |
| Может ли процесс пользователя прочитать/подменить базу | Нет | Прочитать — да (но там шифротекст); подменить политику — обнаружится по MAC (§11.5); откатить базу к старой копии — **не обнаружится** |
| Может ли процесс пользователя подменить бинарники | Нет (`Program Files`, подпись) | **Да** — каталог пользователя, сборка без подписи |
| Что даёт чтение памяти ядра | — | Все ключи, секрет TOTP, `K_policy`, `K_log` (§11.1) |

**Портативный режим — это v0.1** (ставится без прав администратора). **Защищённый режим сделан в 0.2:** `keyholder-service.exe` — служба под `NT SERVICE\KeyHolder`, база в `%ProgramData%\KeyHolder` с DACL «служба + SYSTEM + администраторы» (администраторы вне модели угроз, доступ нужен для установки, удаления и резервных копий; обычные процессы пользователя доступа не имеют), а приложение и `kh` ходят к ядру через канал интерфейса и канал агента. Код ядра общий: он вынесен в `crates/kh-daemon` и одинаково работает внутри приложения и внутри службы.

### 11.5 Криптография и хранение

```
мастер-пароль ──Argon2id(m=256 МБ, t=3, p=4, соль 16 Б)──► KEK (32 Б)
KEK ──XChaCha20-Poly1305──► K_everyday (32 Б, случайный)   — ключи auto/soft
KEK ──XChaCha20-Poly1305──► K_guarded  (32 Б, случайный)   — ключи otp/sealed, TOTP
K_guarded ──HKDF-SHA256──► K_policy (MAC политики), K_log (MAC журнала)
```

- **Каждое значение** шифруется XChaCha20-Poly1305 со случайным 192-битным nonce. В AAD входят: id хранилища, id ключа, версия, раздел и хэш политики. Нельзя переставить шифротекст из одной записи в другую или из раздела `guarded` в `everyday`: расшифровка не пройдёт.
- **Политика подписана.** Уровень, режимы, хосты прокси, правила путей, группа и т. д. закрыты HMAC-SHA256 на ключе `K_policy`. Если кто-то поменял `tier = 'otp'` на `'auto'` прямо в базе, MAC не сойдётся: запись уходит в карантин, в трее — тревога.
- **Параметры Argon2id** калибруются при создании хранилища (~0,5–1 с на этой машине) и хранятся в заголовке.
- **Смена мастер-пароля** перешифровывает только `K_everyday`/`K_guarded`, значения не трогаются.
- **Откат базы.** В базе хранится монотонный счётчик изменений под MAC. В защищённом режиме его копия лежит в хранилище ОС под учёткой службы, и откат обнаруживается. В портативном режиме — нет (остаточный риск).
- **TOTP-секрет** хранится в разделе `guarded`. Сравнение кодов — за постоянное время.
- **Секреты в памяти** — затираются (`zeroize`) при блокировке и после использования. Страницы с ключами шифрования закрепляются (`VirtualLock`, `kh-core/src/mem.rs`) при разблокировке, чтобы не уходить в файл подкачки. Дампы при падении отключены: `keyholder.exe` и `keyholder-service.exe` исключены из Windows Error Reporting (`WerAddExcludedApplication`). Никаких значений в логах, `Debug`-выводе и сообщениях о панике.
- **Ключи службы без мастер-пароля.** В защищённом режиме `K_everyday` и `K_guarded` дополнительно заворачиваются DPAPI под учётной записью службы (`wrap_dpapi`). Служба поднимается после перезагрузки сама; мастер-пароль нужен для создания хранилища, восстановления, смены защиты и выхода из полной блокировки. Посторонний не может развернуть этот блоб: DPAPI привязан к учётной записи, под которой работает служба.
- **Изменяемость защиты.** Смена мастер-пароля перешифровывает только `wrap_everyday`/`wrap_guarded`; анти-фишинговое слово и секрет TOTP перевыпускаются под `K_guarded`.

### 11.6 Разблокировка

- При запуске — мастер-пароль. Без него ядро ничего не выдаёт (запросы агентов получают `locked`, а в трее — просьба разблокировать).
- Автоблокировка после N минут бездействия. В портативном режиме это затирание `K_everyday`, `K_guarded` и всех разрешений. В режиме службы автоблокировка закрывает только интерфейс (агенты продолжают работать по правилам подтверждения); опция «Полная блокировка» заставляет службу забыть ключи до ввода мастер-пароля.
- **Блокировка экрана, сон и выход из системы** закрывают хранилище: приложение держит невидимое message-only окно (`WTSRegisterSessionNotification` + `WM_POWERBROADCAST`), а в режиме службы передаёт это ядру по каналу интерфейса.
- В режиме службы вход в интерфейс настраивается: ничего, PIN или OTP (мастер-пароль остаётся вариантом для портативного режима и для полной блокировки).
- Раздел `guarded` можно настроить на отдельную, более частую блокировку.
- На macOS поле пароля включает Secure Event Input — другие процессы не видят нажатия. На Windows аналога нет: клавиатурный хук того же пользователя увидит пароль (поэтому мастер-пароль один не даёт ничего опасного — см. §11.9, и поэтому позже появится Windows Hello).

### 11.7 Подтверждения и OTP

**Правила OTP**
- RFC 6238: HMAC-SHA1, 6 цифр, шаг 30 с.
- **Один код — одно подтверждение.** Принимается код текущего или предыдущего шага, но только если номер шага **строго больше** последнего принятого. Последний принятый шаг хранится в базе и переживает перезапуск. Значит: повторить код нельзя; два подтверждения за один 30-секундный интервал невозможны — для второго нужен следующий код.
- **Код вводится только в окне KeyHolder.** У MCP нет инструмента «передать OTP».
- **Код принимается только для того запроса, который сейчас на экране** и показан не меньше 1,5 секунды. Запрос после показа неизменяем.
- **Ошибки:** 3 неверных кода для запроса — запрос отклонён, клиент заблокирован до ручного снятия; 5 неверных за 15 минут по всем клиентам — ввод OTP закрыт на 15 минут (дальше — экспоненциально). Вероятность угадать 6 цифр за 3 попытки с учётом двух допустимых шагов — около 6·10⁻⁶ на цикл блокировки, а снятие блокировки требует человека.

**Почему не ввод OTP в чат.** Код TOTP привязан ко времени, а не к запросу. Агент может показать в чате «запрос А: 1 ключ на 15 минут», получить от человека код и отправить его для своего запроса Б «все ключи на 2 часа». Человек видит только то, что написал агент. В окне KeyHolder человек видит сам запрос, а код принимается только для показанного запроса.

**Подключение аутентификатора**
- Секрет TOTP генерирует ядро; QR показывается один раз, в окне с защитой от захвата экрана (§11.8), только после ввода мастер-пароля.
- Перевыпуск — мастер-пароль **и** текущий код (или код восстановления). Одного мастер-пароля мало: иначе перехвативший пароль перевыпустил бы себе OTP.
- 10 одноразовых кодов восстановления показываются при настройке (для печати), хранятся только как хэши SHA-256 (коды случайные, 60 бит, перебор бессмыслен).
- Секрет TOTP не показывается текстом по умолчанию — только QR; текстовый вид — по отдельной кнопке.

**Подтверждение присутствием — сделано для Windows.** `UserConsentVerifier` / Windows Hello (`app/src-tauri/src/hello.rs`): системный диалог подтверждает присутствие человека (PIN/лицо/отпечаток через TPM-ключ). Диалог принадлежит Windows, поэтому ни поддельное окно, ни агент его не заменят, а «переслать» отпечаток нельзя. Доступность проверяется без показа диалога (`CheckAvailabilityAsync`), результат попадает в журнал как `hello`. Используется как альтернатива коду для уровней `pin`/`otp` и для повышения прав; код при этом не нужен, ядро принимает `approval_decide { hello: true }` / `stepup { hello: true }` только от канала интерфейса. Touch ID на macOS (Secure Enclave, `biometryCurrentSet`) остаётся в плане.

### 11.8 Защита окон подтверждения

- **Исключение из захвата экрана.** Windows: `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` — окна подтверждения, окно с QR, окно просмотра значения не попадают на скриншоты и запись экрана, в том числе у агента с computer use. **Но это защищает только картинку**: текст окна по-прежнему доступен через UI Automation (дерево доступности WebView2), а кнопками можно управлять синтетическим вводом. macOS: `NSWindow.sharingType = .none`; по сообщениям разработчиков на macOS 15+ ScreenCaptureKit это игнорирует, поэтому на macOS мы на это **не опираемся** (QR подключаем один раз сразу после установки, до подключения агентов).
- **Анти-фишинговое слово.** При настройке вы выбираете слово; оно показывается в каждом настоящем окне KeyHolder. Слово рисуется картинкой (canvas), а не текстом: его нет в дереве UI Automation и нет на скриншотах (Windows). Это усложняет подделку окна, но **не исключает** её полностью.
- **Фишинг кода поддельным окном — остаточный риск.** Агент может создать настоящий запрос Б, нарисовать поверх своё окно «запрос А» и попросить код; человек вводит код в подделку, агент отправляет его в настоящее окно запроса Б. Правило «код только для показанного запроса» здесь не помогает. Полностью это закрывает только подтверждение присутствием (Windows Hello / Touch ID): системный диалог нельзя подделать, а палец нельзя «переслать». Поэтому присутствие перенесено в v0.2. До тех пор: смотрите на анти-фишинговое слово, и если окно KeyHolder появилось, когда вы ничего не ждали, — отклоняйте.
- **Задержка кнопок.** «Разрешить» становится активной через 1 секунду после появления окна. Кнопки по умолчанию нет, Enter ничего не подтверждает. Окно появляется поверх всех, но не перехватывает фокус клавиатуры, пока по нему не щёлкнули. Это защищает от «окно выскочило под курсор/клавиатуру в момент клика».
- **Отдельный рабочий стол.** Для PIN и OTP, повышения прав и разблокировки ввод идёт на собственном рабочем столе Windows (`CreateDesktopW`/`SwitchDesktop`): чистое Win32-окно без WebView, тёмная тема, что-либо поверх или под ним нарисовать нельзя, синтетический ввод, адресованный обычному рабочему столу, не действует. Рабочий стол возвращается на всех путях, включая отмену и ошибку. Коды и мастер-пароль попадают сразу в ядро и не проходят через webview.
- **Факты отдельно от слов агента.** В окне раздельно показаны то, что проверило ядро (зарегистрированное имя клиента, путь процесса на той стороне канала, время), и то, что прислал агент (причина, рабочая папка) — с пометкой «со слов агента».
- **Текст от агента** — только как текст: управляющие символы и символы смены направления (bidi) вырезаются, длина ограничена (причина — 200 символов).
- **Очередь, склейка повторов, лимиты** (§6) — против «усталости от подтверждений».

### 11.9 Повышение прав (step-up)

Мастер-пароль **и** OTP (позже — или присутствие) нужны для:

- посмотреть или скопировать значение в главном окне;
- заменить значение ключа уровня `otp` или `sealed` (иначе агент через UI-автоматизацию может испортить или подменить ключ);
- экспорт хранилища;
- понизить уровень ключа, разрешить ключу `reveal`/`env`;
- изменить хосты, заголовки и правила путей прокси, изменить рецепты;
- добавить/отозвать клиента, изменить видимость групп для клиента;
- увеличить максимальный срок разрешений;
- снять блокировку клиента, снять отметку «слит» без замены значения;
- перевыпустить TOTP, сменить мастер-пароль, сменить анти-фишинговое слово;
- удалить ключ или всё хранилище.

Без повышения прав: добавить ключ, заменить значение `auto`/`soft`-ключа, повысить уровень, отключить ключ, отозвать разрешение, заблокировать хранилище, изменить описание. Ни одно из этих действий не помогает получить значение.

Поэтому перехваченный мастер-пароль (клавиатурный хук, §11.6) сам по себе не открывает ни значений, ни ослабления политики — нужен ещё код с телефона.

### 11.10 Режимы выдачи: что может утечь

| Режим | Значение в процессах пользователя | Значение в истории агента | Что остаётся агенту |
|---|---|---|---|
| `reveal` | да | **да** — история агента лежит на диске (`~/.claude/projects/…`) и уходит провайдеру модели | считать ключ раскрытым навсегда |
| `env` | да — агент может напечатать `$TOKEN` или прочитать окружение процесса | если напечатает | то же, что `reveal`, только неявно |
| `proxy` | нет — только заглушка | нет | использовать ключ через прокси, пока действует разрешение, и только на разрешённых хостах |
| `sign` | нет | нет | получать подписи разрешённых данных, пока действует разрешение |
| `recipe` | нет (рецепт получает заглушки + прокси) | нет | запускать заранее заданную команду |

Выдача в режимах `reveal` и `env` автоматически ставит ключу статус `exposed` (§9).

Отдельная угроза — **злоупотребление возможностями ключа без его утечки**: имея разрешение на `github/pipod-updates` в режиме `proxy`, агент может, например, удалить ветку. От этого защищают: токены с минимальными правами, правила методов и путей в прокси, короткие сроки разрешений, журнал.

### 11.11 Прокси подстановки — детально

**Запуск**
1. Агент вызывает `prepare_run(keys)` и получает одноразовый билет (60 с, привязан к разрешению и сессии).
2. `kh run --ticket T -- git push` обменивает билет на: заглушки (случайные, в том же формате, что и настоящий ключ, свои для каждого запуска), порт и учётные данные прокси, сертификат УЦ для этого запуска.
3. Дочерний процесс получает: заглушки в переменных; `HTTPS_PROXY`/`HTTP_PROXY=http://run:<пароль>@127.0.0.1:<порт>`; `NODE_USE_ENV_PROXY=1`; сертификат УЦ через `SSL_CERT_FILE` (системные корни + наш), `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`, `GIT_SSL_CAINFO`; для git на Windows — `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0=http.sslBackend`/`GIT_CONFIG_VALUE_0=openssl` (schannel игнорирует `GIT_SSL_CAINFO`).

**УЦ на каждый запуск.** Сертификат УЦ выпускается заново для каждого `kh run`, живёт не дольше разрешения и содержит расширение Name Constraints: он может подписывать **только** хосты из этого запуска. Закрытый ключ УЦ никогда не покидает ядро. В системное хранилище доверия УЦ не ставится. Даже украв сертификат, никто не сможет перехватывать чужой TLS-трафик.

**Поведение прокси**
- Без `Proxy-Authorization` с учётными данными запуска — `407`. Обычные запросы (не прокси-формы) — отказ. CORS-заголовки не отдаются. Веб-страница из браузера прокси воспользоваться не может.
- `CONNECT` к хосту не из списка — прозрачный туннель без расшифровки и без подстановки (заглушка уходит туда как есть и бесполезна).
- `CONNECT` к разрешённому хосту: прокси принимает TLS сертификатом от УЦ запуска, сам открывает TLS к тому же хосту и **проверяет его настоящий сертификат по системным корням**. Ошибка проверки — соединение рвётся, подстановки нет. DNS прокси разрешает сам.
- `Host` / `:authority` запроса должен совпадать с хостом `CONNECT`, иначе `421` и никакой подстановки.
- Подстановка — **только** в настроенном заголовке (по умолчанию `Authorization`: `Bearer X`, `token X`, `Basic base64(user:X)` — в Basic раскодируется, заменяется только пароль, кодируется обратно). Не в URL, не в query, не в теле, не в cookies. Заглушка должна совпасть целиком.
- Необязательные правила методов и путей для ключа: например, только `POST /repos/bifastack/pipod/*`.
- Только HTTPS. Обычный HTTP к разрешённым хостам — без подстановки.
- В запросах к разрешённым хостам прокси убирает `Accept-Encoding`, чтобы ответ шёл без сжатия, и **вычищает из ответа** настоящее значение (а также его base64, base64url, hex, URL-кодированные формы), заменяя его заглушкой. Поиск потоковый (Aho-Corasick), учитывает границы фрагментов.
- Разбор HTTP строгий (hyper): неоднозначные `Content-Length`/`Transfer-Encoding` — отказ. HTTP/1.1 и HTTP/2.
- Каждая подстановка — запись в журнале: хост, метод, путь, статус ответа.

**Ограничения.** Инструменты, которые игнорируют `HTTPS_PROXY` или закрепляют сертификаты, через прокси не работают — для них `recipe`. Утилиты на Go на Windows/macOS проверяют сертификаты системным верификатором и игнорируют `SSL_CERT_FILE` (по сообщениям, это меняется в Go 1.27 через отдельную настройку). Для них — необязательный постоянный УЦ с Name Constraints в пользовательском хранилище доверия (ставит человек, один раз), закрытый ключ — по-прежнему только в ядре.

### 11.12 Каналы связи

- **TCP-слушатель только один** — прокси, на `127.0.0.1`, случайный порт, только с учётными данными запуска.
- **Канал агента** — Windows: named pipe `\\.\pipe\keyholder-<хэш SID>`; DACL — только текущий пользователь и SYSTEM; удалённые клиенты отклоняются; сервер создаёт канал с `FILE_FLAG_FIRST_PIPE_INSTANCE`. macOS: unix socket в каталоге с правами `0700`; в защищённом режиме — проверка `getpeereid`.
- **Захват имени канала.** Чужой процесс может создать канал с тем же именем раньше KeyHolder и притвориться им (собирать токены клиентов, показывать фальшивые окна). Поэтому: KeyHolder создаёт канал с `FILE_FLAG_FIRST_PIPE_INSTANCE` и, если имя уже занято, **не работает и показывает тревогу**; `kh mcp` проверяет сервер: `GetNamedPipeServerProcessId` → путь образа → в защищённом режиме ещё и подпись. В v0.1 (без подписи, бинарники в каталоге пользователя) проверка пути слабая: тот, кто может подменить файлы, обходит её.
- **Токены клиентов** — 256 бит, в базе только SHA-256. Токен нужен для журнала и видимости групп. **Это не граница безопасности**: токены лежат в конфигах MCP, которые читает любой процесс пользователя. Безопасность держится на подтверждениях.
- **Нет HTTP-MCP** — нет DNS rebinding и CSRF.
- **Команды интерфейса** вызываются внутри процесса приложения (Tauri IPC), а не через канал агента. Через канал агента доступен только протокол агента; действия управления через него недоступны.

### 11.13 Интерфейс как поверхность атаки (Tauri)

- Строгий CSP: `default-src 'self'`, без `eval`, без внешних ресурсов.
- В webview включены только наши команды; плагинов `shell`, `fs`, `http` для webview нет. Файлы для импорта читает Rust-код по путям, которые выбрал человек в системном диалоге.
- Всё, что пришло от агента (причина, комментарий об утечке, имя клиента из `clientInfo`), выводится только как текст; React экранирует по умолчанию, `dangerouslySetInnerHTML` запрещён.
- Существующие значения в webview не отправляются никогда, кроме окна просмотра после повышения прав (короткое время, исключено из захвата экрана). Поле значения в форме — только на запись.
- DevTools в релизной сборке отключены.

### 11.14 Буфер обмена, скриншоты, файл подкачки

- **Копирование значения** (после повышения прав): Windows — форматы `ExcludeClipboardContentFromMonitorProcessing`, `CanIncludeInClipboardHistory = 0`, `CanUploadToCloudClipboard = 0`; macOS — `org.nspasteboard.ConcealedType`. Буфер очищается через 30 секунд, если там всё ещё наше значение. В интерфейсе предупреждение: за эти 30 секунд буфер может прочитать любой процесс пользователя.
- **Скриншоты** — §11.8.
- **Файл подкачки / гибернация.** `VirtualLock`/`mlock` уберегают ключи шифрования от подкачки, но не от `hiberfil.sys` при гибернации. Рекомендация — шифрование диска (BitLocker / FileVault); KeyHolder блокируется перед сном.

### 11.15 Журнал

- Только добавление. Запись: `seq, ts, client, session, action, target, outcome, detail`.
- `hash = SHA-256(prev_hash ‖ запись)`, `mac = HMAC(K_log, hash)`. Подделать запись или пересчитать цепочку без `K_log` нельзя. В портативном режиме `K_log` читается из памяти процесса (§11.1), поэтому там цепочка ловит правку файла базы, но не того, кто читал память; от него защищает только внешний якорь.
- Счётчик записей и «голова» цепочки хранятся под MAC — обрезка хвоста обнаруживается. Для сильной гарантии — внешний «якорь»: по желанию голова цепочки периодически отправляется наружу (файл на другом диске, Telegram).
- Проверка цепочки — при запуске и по кнопке. Значок «Цепочка хэшей цела» в журнале.
- Значения ключей в журнал не пишутся никогда. Текст от агента хранится как данные.
- Старые записи можно удалить через «контрольную точку» — запись, которая фиксирует голову удаляемого отрезка, чтобы цепочка оставалась проверяемой.

### 11.16 Резервные копии и восстановление

- **Сброс хранилища** (забыт мастер-пароль): на экране входа — «Сбросить хранилище» с подтверждением словом СБРОСИТЬ. Текущий файл не удаляется, а переименовывается в `vault.db.reset-<время>` (он зашифрован и откроется прежним паролем), на его месте создаётся пустое хранилище. Агентам понадобятся новые токены.

- **Перенос хранилища — файл `.mcpkey`** («Настройки» → «Перенос хранилища»; на экране первого запуска — «Перенести хранилище из файла .mcpkey»). В файле всё хранилище: ключи, клиенты агентов, настройки, журнал, аутентификатор. Копия базы шифруется ещё раз (XChaCha20-Poly1305, ключ — HKDF от K_guarded), поэтому не видны и имена ключей. В заголовке — соль, параметры Argon2id и обёрнутый K_guarded, так что файл открывается одним мастер-паролем на момент экспорта, без DPAPI и без привязки к машине; обёртка DPAPI службы в файл не попадает. Заголовок входит в AAD. Экспорт требует повышения прав. Загрузка в пустое хранилище — сразу; поверх существующего — только когда оно открыто и после повышения прав; прежний файл остаётся рядом как `vault.db.before-import-<время>`. Мастер-пароль файла вводится на отдельном рабочем столе.
- Забыли мастер-пароль — данные не восстановить. Это свойство, а не ошибка.
- Потеряли телефон — мастер-пароль + код восстановления → новый TOTP.
- Расшифрованного экспорта нет.

### 11.17 Обновления и цепочка поставок

- Минимум зависимостей; `Cargo.lock` и `package-lock.json` в репозитории; `cargo deny` (уязвимости, лицензии, источники) и `npm audit` в CI.
- Релизы подписаны: Authenticode на Windows, Developer ID + нотаризация на macOS.
- Обновления только с проверкой подписи (Tauri updater, minisign); без подписи — не устанавливаются.
- В защищённом режиме бинарники лежат в каталогах, куда пользователь писать не может (`Program Files`), — агент не подменит `kh.exe` или приложение.

### 11.18 Остаточные риски

| Риск | Почему остаётся | Что делать |
|---|---|---|
| Агент или вредонос с правами администратора/root | Может всё: читать память службы, ставить драйверы | Не запускать агентов с правами администратора; не выключать UAC; не давать `sudo` без пароля |
| Портативный режим на Windows: чтение памяти KeyHolder.app процессом того же пользователя | Нет границы учётных записей | Защищённый режим (служба) |
| Портативный режим: откат базы к старой копии | Негде хранить защищённый счётчик | Защищённый режим |
| Клавиатурный хук на Windows видит мастер-пароль и цифры OTP при вводе | Нет Secure Input для обычных приложений | Пароль один ничего не даёт (§11.9); OTP одноразовый и привязан к показанному запросу; позже — Windows Hello |
| Мягкое подтверждение может нажать агент | UI-автоматизация того же пользователя | Всё ценное — на `otp` |
| Текст окон подтверждения читается через UI Automation; код можно выманить поддельным окном | Окно живёт в сессии пользователя в любом режиме | Анти-фишинговое слово картинкой; подтверждение присутствием (v0.2) |
| Портативный режим: подмена `KeyHolder.exe`/`kh.exe` | Каталог пользователя, нет подписи | Защищённый режим, подписанные сборки |
| Портативный режим на Windows: чтение памяти даёт секрет TOTP, `K_policy`, `K_log` | См. §11.1 | Защищённый режим |
| `reveal`/`env` раскрывают значение | Так задуманы | Для ценных ключей — `proxy`/`sign`/`recipe`; статус `exposed`; ротация |
| Злоупотребление ключом через прокси | Ключ работает, пока действует разрешение | Минимальные права токенов, правила путей, короткие сроки, журнал |
| Скриншот окна с QR на macOS 15+ | ScreenCaptureKit игнорирует `sharingType` | Подключать аутентификатор сразу после установки, до агентов; при сомнении — перевыпустить |
| Буфер обмена в течение 30 с | Буфер общий для всех процессов | Не копировать без нужды; предупреждение в интерфейсе |
| Гибернация | Память пишется на диск | Шифрование диска |
| Скомпрометирован телефон | OTP перестаёт быть «чужим» | Touch ID / Windows Hello как второй фактор |

### 11.19 Атаки, которые обязаны провалиться (приёмочные тесты)

1. Агент читает `vault.db` — видит только шифротекст.
2. Агент меняет в базе `tier` ключа с `otp` на `auto` — запись уходит в карантин, тревога, ключ не выдаётся.
3. Агент переставляет шифротекст из `guarded`-ключа в `auto`-ключ — расшифровка не проходит.
4. Агент вызывает `get_secret` для ключа вне разрешения — `not_in_grant`, запись в журнале.
5. Агент вызывает `get_secret` для `proxy`-ключа внутри разрешения — отказ (режим не `reveal`).
6. Агент запрашивает `sealed`-ключ — ключ вырезан из запроса, в окне видно «запечатан, убран».
7. Тот же код OTP вводится дважды — второй раз отказ.
8. Два запроса за 30 секунд — второй ждёт следующий код.
9. Агент создаёт запрос Б, пока на экране запрос А, и отправляет код — код принимается только для А.
10. Агент подменяет запрос на экране (отклоняет А, сразу показывается Б) и отправляет код за 1,5 с — отказ.
11. Три неверных кода — клиент заблокирован; ещё два с другого клиента — ввод OTP закрыт на 15 минут.
12. Агент печатает переменную с заглушкой — видит заглушку.
13. Агент отправляет заглушку на `httpbin.org` через прокси — уходит заглушка, в журнале отказ подстановки.
14. Агент кладёт заглушку в тело запроса к `api.github.com` — подстановки нет.
15. Агент подключается к прокси без учётных данных запуска — `407`.
16. Веб-страница делает `fetch("http://127.0.0.1:<порт>/")` — отказ, без CORS.
17. Ответ разрешённого хоста содержит настоящее значение (в т. ч. в base64) — агент получает заглушку.
18. Чужой процесс создаёт named pipe KeyHolder до запуска приложения — `kh mcp` отказывается с ним работать.
19. Причина запроса содержит HTML, `<script>` и bidi-символы — в окне виден безопасный текст.
20. Агент через UI-автоматизацию пытается открыть просмотр значения — нужен мастер-пароль и OTP.
21. Агент через UI-автоматизацию понижает уровень ключа — нужен мастер-пароль и OTP.
22. Запись журнала удалена или изменена в базе — проверка цепочки показывает разрыв.
23. `check_leak` с текстом, где есть только половина значения, — совпадения нет.
24. `check_leak` с 10 000 вариантов коротких паролей — короткие значения в поиске не участвуют.
25. Скриншот экрана (Windows) во время показа окна OTP — окна на снимке нет.

## 13. Стек

- **Rust**: ядро и CLI. `rusqlite` (SQLite встроен), `argon2`, `chacha20poly1305`, `hkdf`, `hmac`, `sha2`, `sha1`, `secrecy`, `zeroize`, `rand`, `serde`, `tokio` (named pipe / unix socket); прокси — `hyper` + `rustls` + `rcgen`.

### Что реально сделано в v0.1 (30.10.2026)

Сделано: всё из строки v0.1 выше, плюс режим `env` с `prepare_run` / `kh run` и `kh scan` (перенесены из v0.2, потому что значение в них хотя бы не проходит через чат).

Проверено: 20 модульных тестов ядра (шифрование, подмена политики и шифротекста, повтор OTP, правка и обрезка журнала, поиск утечек) и сквозной тест через настоящий `kh mcp` → приложение → окна подтверждения (20/20: автовыдача, отказ вне разрешения, вырезание запечатанного ключа, мягкое окно, неверный и верный OTP, `kh run` с одноразовым билетом, `check_leak`, `report_leak`, лимит запросов).

### Что сделано в 0.2

- **Режим службы.** Ядро вынесено в `crates/kh-daemon` и не знает про окна: события наружу уходят через трейт `Events`, команды интерфейса — через `call(method, params)`. `keyholder-service.exe` (`install` / `uninstall` / `--console`) ставит службу под `NT SERVICE\KeyHolder`, закрывает `%ProgramData%\KeyHolder` на «служба + SYSTEM + администраторы», хранит ключи под DPAPI и поднимается после перезагрузки сам.
- **Два канала с разными DACL:** канал агента и канал интерфейса. Команды интерфейса через канал агента недоступны. `kh` проверяет владельца канала: двоичный файл KeyHolder из своего каталога и, для службы, учётную запись службы.
- **Отдельный рабочий стол** для PIN, OTP, мастер-пароля и повышения прав (`app/src-tauri/src/desktop.rs`), настройка «Подтверждать на отдельном рабочем столе» (включена по умолчанию), отладочный обход `KH_NO_SECURE_DESKTOP=1`.
- **Пресеты разрешений**, склейка одинаковых запросов, блокировка при блокировке экрана и сне, `VirtualLock`, исключение из WER-дампов, внешний якорь журнала, перевыпуск аутентификатора, коды восстановления, смена мастер-пароля и анти-фишингового слова.

Осталось из §14: Touch ID и LaunchDaemon под macOS, режимы `proxy` / `sign` / `recipe`, подписанные релизы.

Порядок v0.2 выбран по итогам ревью безопасности: две главные дыры портативного режима — чтение памяти процесса и фишинг кода поддельным окном — закрываются именно защищённым режимом и присутствием.
